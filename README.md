# FHE Accelerator Simulators

How long does a CKKS bootstrap take on a given accelerator? Is the design bound by NTT throughput or by evaluation-key traffic? How much on-chip SRAM stops key traffic dominating, and does an optical NTT engine win once conversion energy and precision corrections are counted? Five interactive decks and a tested SimPy simulator work through these questions. They run from CKKS as a hardware workload and the anatomy of bootstrapping, through the simulator itself (**live in the browser**, a bit-exact JavaScript port) and optical transform engines, to design-space results, a reading list and practice questions.

**Live index:** https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/

## Headline results

* A baseline bootstrap on the ARK-class design takes 13.94 ms and is memory-bound: evaluation keys are 6.74 GB of the 12.44 GB of HBM traffic.
* Min-KS, seeded keys and on-the-fly plaintexts cut it to 7.19 ms (MAC-bound); on an NTT-starved design the same techniques make it slower (17.46 ms to 26.65 ms).
* Area, the third axis (7 nm, illustrative): the ARK-class die is 457.9 mm². Memory-bound, 128 MiB more SRAM saves 3.74 ms per 100 mm² added against 0.21 ms for doubling the compute.

Every number is read from [examples/results.md](https://github.com/BrendanJamesLynskey/FHE_Accelerator_Sim/blob/main/examples/results.md) when this README is built. Hardware coefficients are illustrative.

## Glossary: concepts and where they are explained

Every concept the decks rely on, with links to the slides that explain it in depth (this series, the Cryptography decks, or LLM Inference Simulators). The same glossary, with anchors each deck links to, is on the [live index](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#glossary).

| Concept | What it is | Where it is explained |
|---|---|---|
| LWE and Ring-LWE | The hard problems FHE rests on: given noisy linear equations b = a·s + e (mod q), recovering s is hard. Ring-LWE works with polynomials instead of vectors, so one sample carries N coefficients, which is what makes NTTs the core kernel. | [Cryptography 08 · LWE](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/4); [Cryptography 08 · Ring-LWE](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/5) |
| CKKS | The FHE scheme for approximate arithmetic on real or complex vectors. Values are encoded with a scale Δ; noise is treated as rounding error; each multiplication is followed by a rescale that consumes one level. | [Cryptography 08 · CKKS](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/10); [FHESim 01 · noise, scale and levels](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-06) |
| RNS polynomials and limbs | The ciphertext modulus Q is a product of word-sized primes, so each polynomial is stored as one row ('limb') of N residues per prime. A ciphertext at level ℓ has ℓ+1 limbs; all arithmetic stays in 64-bit words. | [FHESim 01 · the data: RNS polynomials](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-03); [Cryptography 08 · RNS and NTT](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/16) |
| Number-theoretic transform (NTT) | The FFT over a finite field Z_q. It moves a limb between coefficient and evaluation form in (N/2) log N butterflies, so polynomial multiplication becomes element-wise. Every key switch and rescale runs NTTs. | [Cryptography 08 · RNS and NTT](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/16); [Cryptography 10 · the NTT](https://brendanjameslynskey.github.io/Cryptography/10-crypto-hardware-accelerator-design/#/13); [Cryptography 10 · NTT hardware architectures](https://brendanjameslynskey.github.io/Cryptography/10-crypto-hardware-accelerator-design/#/14); [FHESim 01 · primitive kernels](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-05) |
| Modular reduction (Barrett, Montgomery) | Ways to compute a·b mod q without division, using precomputed constants. Every butterfly and multiply-add lane in an FHE accelerator contains one. | [Cryptography 10 · Montgomery reduction in SystemVerilog](https://brendanjameslynskey.github.io/Cryptography/10-crypto-hardware-accelerator-design/#/29); [Cryptography 10 · the NTT](https://brendanjameslynskey.github.io/Cryptography/10-crypto-hardware-accelerator-design/#/13) |
| Levels, scale and rescale | A multiplication squares the scale; rescale divides by a prime and drops a limb. So each multiplicative level costs one prime, the level of a ciphertext sets how much work every operation on it does, and level 0 cannot be multiplied. | [FHESim 01 · noise, scale and levels](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-06); [Cryptography 08 · noise growth](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/6) |
| Automorphism and slot rotation | Substituting X → X^(5^r) permutes a polynomial's coefficients so that the packed slots rotate by r. The permutation is free of arithmetic, but the result needs a key switch with a rotation key specific to r. | [FHESim 01 · primitive kernels](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-05); [FHESim 02 · BSGS rotations](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-04) |
| Key switching and evaluation keys | After a multiplication (relinearisation) or a rotation, part of the ciphertext is under the wrong key; key switching fixes it using an evaluation key (78–210 MiB for the N = 2^16 sets used here). It dominates the cost of FHE. | [FHESim 01 · key switching, step by step](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-07); [FHESim 01 · why key switching dominates](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-08); [Cryptography 08 · relinearisation and key switching](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/15) |
| Hybrid key switching: dnum, special primes, ModUp and ModDown | The limbs are split into dnum digits of α limbs. Each digit is base-converted up to Q·P (ModUp, with α special primes P), multiplied by the key, and converted back (ModDown). dnum trades key size against work and security. | [FHESim 01 · key switching](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-07); [FHESim 01 · the dnum trade-off](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-10) |
| Base conversion | Re-expresses an RNS polynomial in a different set of primes, as a matrix product over limbs. It is the heart of ModUp and ModDown and often the second-largest cost after NTTs. | [FHESim 01 · primitive kernels](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-05) |
| HMult, HRot, PMult, CMult | The homomorphic operations: ciphertext×ciphertext multiply (with relinearisation), rotation, ciphertext×plaintext multiply and ciphertext×constant multiply. Only HMult and HRot need a key switch. | [FHESim 01 · why key switching dominates](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-08); [FHESim 02 · operation counts per stage](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-08) |
| Slots, packing and sparse packing | A CKKS ciphertext holds N/2 complex numbers in parallel 'slots' (SIMD). Using fewer slots (sparse packing) shrinks the bootstrap's DFTs but adds a SubSum of rotations. | [FHESim 01 · RNS polynomials](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-03); [FHESim 02 · ModRaise and SubSum](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-02) |
| Bootstrapping | Evaluating decryption homomorphically to turn a level-0 ciphertext into one at a high level: ModRaise, CoeffToSlot, EvalMod, SlotToCoeff. It costs hundreds of key switches and gigabytes of keys. | [FHESim 02 · why bootstrap](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-01); [Cryptography 08 · bootstrapping](https://brendanjameslynskey.github.io/Cryptography/08-fully-homomorphic-encryption/#/13) |
| ModRaise | Reinterprets a level-0 ciphertext modulo the full Q, which adds a multiple of q_0 the rest of bootstrapping must remove. Cheap: transforms only. | [FHESim 02 · ModRaise](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-02) |
| CoeffToSlot and SlotToCoeff (homomorphic DFT) | The encoding transform and its inverse, evaluated homomorphically as a few sparse matrix-vector products (an FFT factorised into levels). Rotation- and key-heavy: the memory-bound part of bootstrapping. | [FHESim 02 · CoeffToSlot](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-03); [FHESim 02 · SlotToCoeff](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-06) |
| Baby-step giant-step (BSGS) | Evaluates a d-diagonal matrix with about 2√d rotations instead of d: n_1 baby-step rotations of the input, n_2 inner sums, and one giant-step rotation per sum. | [FHESim 02 · BSGS rotations](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-04) |
| Hoisting | Several rotations of the same ciphertext share one decomposition and ModUp (Halevi and Shoup), saving NTTs; the rotation keys stay distinct. | [FHESim 02 · BSGS rotations](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-04) |
| EvalMod: Chebyshev series and double angle | Approximates the modular reduction with a scaled cosine evaluated as a Chebyshev series (baby-step giant-step polynomial evaluation) followed by double-angle steps cos 2x = 2cos²x − 1. Multiplication-heavy, one key. | [FHESim 02 · EvalMod](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-05) |
| SlotToCoeff first | Running SlotToCoeff before ModRaise, on the nearly exhausted input: cheap keys, one EvalMod for real data, and its levels are not taken from the top. OpenFHE's BTSlotsEncoding. | [FHESim 02 · ordering variants](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-02); [FHESim 05 · acceleration techniques](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-04) |
| Min-KS, seeded keys and on-the-fly plaintexts | Algorithmic ways to cut key and plaintext traffic: rotate iteratively by one step so a BSGS loop reuses one key (Min-KS, from ARK), regenerate half of each key from a seed, and generate DFT plaintexts on chip. | [FHESim 02 · algorithmic levers](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-11); [FHESim 05 · acceleration techniques](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-04); [ARK (arXiv:2205.00922)](https://arxiv.org/abs/2205.00922) |
| Lazy ModDown (OpenFHE's BSGS) | Keeping rotated ciphertexts in the extended Q·P basis and doing one ModDown per DFT level, so baby steps cost no NTTs and many more of them are used. Fewer NTTs, more keys. | [FHESim 02 · checked against OpenFHE](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-12); [FHESim 02 · algorithmic levers](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-11) |
| Amortised time per slot (T_A.S.) | Bootstrap time plus the multiplications it enables, divided by the levels left and the slots: the cost per useful operation. Used by ARK and the 100x GPU paper to compare different parameters. | [FHESim 02 · where the levels go](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-07); [ARK (arXiv:2205.00922)](https://arxiv.org/abs/2205.00922) |
| FLEXIBLEAUTO rescaling (OpenFHE) | An OpenFHE mode that rescales automatically and lazily, before each multiplication, on copies of its inputs. Convenient for users; in a kernel trace it shows up as many extra rescales. | [FHESim 02 · checked against OpenFHE](https://brendanjameslynskey.github.io/FHESim_02_Anatomy_of_Bootstrapping/#slide-12) |
| Scratchpad, LRU and spills | The accelerator's on-chip SRAM, modelled as a least-recently-used store of ciphertexts, keys and plaintexts. A miss loads from HBM; evicting a live ciphertext writes it back (a spill). | [FHESim 03 · scratchpad and traffic](https://brendanjameslynskey.github.io/FHESim_03_Simulating_an_FHE_Accelerator/#slide-06); [FHESim 05 · SRAM against key traffic](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-02) |
| Silicon area and the area model | Die area in mm² per component (NTT, MAC and permutation units, scratchpad, uncore, HBM PHYs). The simulator's model is at 7 nm, calibrated from ARK's published breakdown and a CACTI sweep, and illustrative; area never changes a simulated time or energy. | [FHESim 05 · SRAM against key traffic and area](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-02); [SimEng 13 · what sets area](https://brendanjameslynskey.github.io/SimEng_13_PPA_Tradeoffs/#slide-04); [SimEng 13 · estimating area before layout](https://brendanjameslynskey.github.io/SimEng_13_PPA_Tradeoffs/#slide-05) |
| Die yield and silicon cost | The fraction of dies with no fatal defect: Poisson e^(−A·D_0) or Murphy's model, which is kinder to large dies. With dies per wafer it turns area into cost per good die, which grows faster than area. | [SimEng 13 · why area is cost](https://brendanjameslynskey.github.io/SimEng_13_PPA_Tradeoffs/#slide-06); [SimEng 13 · when to split the die](https://brendanjameslynskey.github.io/SimEng_13_PPA_Tradeoffs/#slide-11) |
| HBM and key streaming | Off-chip high-bandwidth memory. Evaluation keys and DFT plaintexts are too big to keep on chip, so they stream from HBM, which is why bootstrapping is often memory-bound. | [FHESim 03 · the modelled architecture](https://brendanjameslynskey.github.io/FHESim_03_Simulating_an_FHE_Accelerator/#slide-02); [FHESim 01 · why key switching dominates](https://brendanjameslynskey.github.io/FHESim_01_FHE_for_Hardware_Engineers/#slide-08) |
| Roofline and ridge point | Performance is capped by compute or by memory bandwidth; the ridge point is the arithmetic intensity where the two meet. Work below it is memory-bound. | [LLM Inference Simulators 03 · the roofline](https://brendanjameslynskey.github.io/InfSim_03_LLM_Inference_Workloads/#slide-04); [FHESim 05 · NTT-bound against memory-bound](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-03) |
| NTT-, MAC-, memory- and power-bound | The simulator's verdict: the most-utilised resource sets the bound (HBM, NTT units, multiply-add lanes), or power when the power limit throttles a compute-bound design. | [FHESim 03 · metrics and hot-spots](https://brendanjameslynskey.github.io/FHESim_03_Simulating_an_FHE_Accelerator/#slide-08); [FHESim 05 · regimes](https://brendanjameslynskey.github.io/FHESim_05_Results_and_Design_Space/#slide-03) |
| Hot-spot attribution | For each stage of the workload, the resource that was busiest: where an upgrade would help. | [LLM Inference Simulators 06 · hot-spot attribution](https://brendanjameslynskey.github.io/InfSim_06_Metrics_Hotspots_Validation/#slide-04); [FHESim 03 · metrics and hot-spots](https://brendanjameslynskey.github.io/FHESim_03_Simulating_an_FHE_Accelerator/#slide-08) |
